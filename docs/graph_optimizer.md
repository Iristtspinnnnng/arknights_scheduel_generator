# 图卷积优化器：数据审计、算法与实测对照

本文记录把房间组合搜索从「全量枚举 + 混合局部搜索」换成「静态图卷积短名单 + 精确复核」的
决策依据、实现细节和实测结果。

---

## 1. 仓库里到底有没有足够的静态图信息？

结论：**结构信息足够，数值强度不足**。所以做法是「用图给出结构先验，用现有生产模拟器当老师
标定数值」。

用 `graph-audit` 在本地 `data/cache`（`Stream://torappu-data/v074/rel74.0`，734 个 buff，
418 个可进基建的干员）和示例满练表（447 行 → 合并同名后 438 名干员）上实测：

| 项目 | 数值 | 来源 |
| --- | --- | --- |
| 干员节点 | 438 | 练度表 × `character_table.json` |
| 特征宽度 | 24 | 见 §2.1 |
| 阵营/势力组 | 55 | `character_table.json` 的 `nationId` / `groupId` / `teamId`（含 `mainPower` / `subPower`），经 `data.py:faction_tags_for_char` 归一化 |
| 阵营边 | 13584 | 同组两两相连，权重按组规模衰减 |
| 点名羁绊边 | 72（36 对） | 技能文本里点了另一位干员的名字 |
| 组合机制边 | 2252 | 技能文本命中「当与 / 同一个贸易站 / 归零 / 低语 / 特别订单 / 高价值订单 / 回收利用 / 仓库容量 …」 |
| 孤立干员 | 36 | 35 名「支援机械」/剧情干员，无阵营无队友，对排班无羁绊影响 |

### 1.1 真实存在的「羁绊」有四类，不是一张成对权重表

读 `production.py` / `skill_rules.py` 后确认，游戏里生效的协同只有这四种形态：

1. **阵营计数型**：`skill_rules.py:342-451` 的 13 条硬编码分支，公式形如
   `+20 × 本房间 glasgow 人数`、`+3 × min(全基建 rhine 人数, 5)`。
   → 图上就是**阵营超节点 + 求和聚合**，这是图卷积最自然能表达的东西。
2. **点名干员型**：`凛御银灰`、`能天使`、`推进之王/维娜·维多利亚`、`古米`、`阿米娅` 等字面量。
   → 图上就是 `named` 边。实测 36 对，包括 `德克萨斯 ↔ 拉普兰德`、`蕾缪安 ↔ 能天使`、
   `烈夏 ↔ 古米`、`维希戴尔 ↔ 伊内丝/赫德雷`。
3. **阶跃查表型**：`production.py:64-315` 的 guide 刊例表——16 行龙门币贸易、1 行合成玉贸易、
   3 行制造。命中即**用刊例值覆盖**干员技能计算（`evaluate_trading` / `evaluate_manufacture`），
   所以这是**阶跃函数**，线性读出层学不出来。例如但书 + 两名 45% 伙伴 → 200%，
   巫恋 + 龙舌兰 + 但书 → 207%。
4. **同房间条件文本型**：`当与X在同一个贸易站时…`，由 `skill_rules.py:284-301` 正则匹配。

### 1.2 缺口：数值强度不在数据里

- `buff.efficiency` 对绝大多数技能是 0，真实数值藏在 `description` 文本里，
  由 `data.py:parse_skill_score` 取「描述里最大的 `+N%`」。这是粗糙的一阶近似。
- 阵营计数、阶跃查表、心情消耗这些**条件与非线性**，是代码里的硬编码逻辑，不是数据字段。

所以新优化器**不自己定义收益**：它把 `ProductionSimulator` 当作老师，用它的输出拟合读出层。
换句话说，图提供结构归纳偏置，模拟器提供数值监督。

## 2. 算法

### 2.1 节点特征（`graph_features.py`，24 维，全部确定、可复现）

| 组 | 维度 | 内容 |
| --- | --- | --- |
| 练度 | 6 | 星级、精英化、等级、潜能、技能等级、最高专精 |
| 房型能力 | 7 | 各房型的最强 `parsed_score` / 归一化常数 |
| 产物亲和 | 5 | `O_GOLD` / `O_DIAMOND` / `F_GOLD` / `F_EXP` / `F_DIAMOND` |
| 结构标记 | 6 | 复杂条件比例、是否有未解锁技能、阵营数、点名度数、组合机制标记、guide 锚点 |

编码器会额外拼上 7 个房型能力的平方项（共 31 维输入），让线性读出层能表达产能饱和的凹性。

### 2.2 三类边与阵营超节点

- `faction`：同组两两相连，权重 `1/log2(2+组规模)`，超过 60 人的阵营（`rhodes` 94 人）**不建边**，
  否则整张图退化成全连接、小团体的信号被稀释。
- `named`：技能文本点名 → 双向边，权重 1.5。
- `combo`：命中组合机制 → 只在**该技能所属房型内**连接，权重 0.4。

传播时 `faction` 不走 O(n²) 边表，而是**超节点均值**：
每个阵营组先算组内均值，再对干员取其所属组的均值。数学上等价于完全子图的行归一化聚合，
复杂度从 O(组²) 降到 O(节点数)；`rhodes` 这种大组也不会变成全连接。

### 2.3 固定超参图卷积（`graph_conv.py`）

```
h'[i] = act( ws·W_self·h[i] + Σ_r wr·W_r·(A_r h)[i] )
```

- `W_*` 是**确定性稀疏随机投影**（SplitMix64 播种，每通道 3 个非零）。所以前向传播跨平台、
  跨进程、跨运行完全一致；没有训练循环、没有 torch/numpy 依赖、不需要 GPU。
  这是 Gaussian random feature 的思路：随机投影负责把结构摊开，学习只发生在最后一层。
- 关系权重固定：`faction 0.55 / named 1.30 / combo 0.45`（羁绊比阵营更具体，给更高的权重）。
- 嵌入 = 原始特征 ⊕ 每层隐表示，默认 `31 + 2×8 = 47` 维。

### 2.4 闭式读出层：一元 + 二元协同

对房间组合 `S`：

```
ŷ(S) = b + Σ_{i∈S} w_u·e_i + Σ_{i<j∈S} w_p·(e_i ⊙ e_j) + 房间项
```

这正是「单人贡献 + 两人同房才生效的增益」的结构。权重用**岭回归正规方程 + 高斯-约当消元**
闭式求解（47 维嵌入 → 99 个参数，毫秒级），无需梯度下降。

训练标签来自 `ScheduleOptimizer._score_room_combo`（即模拟器的房间分数），采样 288 个
1~满编的组合。实测 holdout 质量：

| 房间 | 目标 | R²(holdout) | MAE | MAE/均值 | Spearman |
| --- | --- | --- | --- | --- | --- |
| TRADING | O_GOLD | 0.865 | 2.00 | 6.3% | 0.95 |
| TRADING | O_DIAMOND | 0.753 | 13.75 | 7.1% | 0.94 |
| MANUFACTURE | F_EXP | 0.696 | 1.72 | 6.9% | 0.86 |
| MANUFACTURE | F_GOLD | 0.571 | 6.35 | 5.0% | 0.90 |
| MANUFACTURE | F_DIAMOND | 0.755 | 3.58 | 4.7% | 0.97 |

> `TRADING/O_DIAMOND` 一行在 O_DIAMOND 校准 v2 之前是 **R² = −110.6 / MAE 18.5 / Spearman 0.30**：
> guide 刊例把 L3 合成玉贸易站固定成 132%，标签方差小到没有信息（代码会检测这种情况并退化成
> 常数模型）。校准 v2（§6 第 2 条）之后同一间房有了真梯度，R² 才回到 0.75。
> 每次改产能校准都要**同时**作废旧缓存（`graph_cache.CACHE_SCHEMA_VERSION`），
> 否则读出层还按旧标签拟合。

### 2.4b 显式羁绊基：把「羁绊值多少分」写出来

图卷积只给**结构**，数值强度靠 47 维嵌入去凑——这不够，因为游戏里两种羁绊
本来就是**可加 / 可配对**的：

* 阵营计数型（`+20 × 本房 glasgow 人数`）对同房干员可加 → 塞进**一元项**；
* 点名羁绊型（`当与德克萨斯在同一个贸易站时…`）只在两人同房时生效 → 塞进**二元项**。

所以读出层的基扩成两段：图嵌入基 + 显式羁绊基（`graph_bonds.py`）。
系数由岭回归闭式解出，可以直接读（注意：这些阵营列彼此相关性高，岭回归会把权重
分摊到同族标签上，所以**绝对值只有排名意义**，不要逐条当成游戏内真实公式）：

| 房间 / 目标 | 特征 | 学到的系数 |
| --- | --- | --- |
| TRADING / O_GOLD | `faction_count:victoria` | +9.63 分 / 人 |
| TRADING / O_GOLD | `faction_count:laterano` | +8.41 分 / 人 |
| TRADING / O_GOLD | `bond:A_mentions_B`（A 点名 B） | +1.77 分 / 对 |

三个关键取舍（都是实测出来的，不是猜的）：

1. **必须按「房间 × 产物」筛选**。黑钢（`+2 × min(全基建黑钢人数,3)`）和莱茵用的是
   **全基建**计数、机械精通用**发电站**计数，把它们当成房间级一元项只会加噪声——
   实测制造站 holdout R² 从 0.75 掉到 0.70。现在只有
   `IN_ROOM_COUNT_TAGS` 里语义成立的组合才开（贸易: glasgow/laterano/mh2；
   制造 F_EXP: A1/ussg；发电: op/laterano）。
2. **别名标签要按成员集合去重**（`rhine`/`rh`、`blacksteel`/`bs`、`knight`/`kazimierz`），
   否则列完全共线，岭回归既不稳也没法解释。
3. **羁绊基要单独加强收缩**（`bond_ridge_scale=4`）：列少、样本少，用列缩放
   把它的有效惩罚放大 4 倍。

效果（贸易站 O_GOLD，最重要的房间）：R² 0.8206 → **0.8649**，
MAE 2.382 → **1.997**，Spearman 0.907 → **0.950**。制造站基本中性（±1pp），
因为它们的阵营机制本来就不是房间内计数。

### 2.5 从「全量枚举」到「短名单 + 精确复核」

旧算法对一个房间做 `C(32,3)=4960` 次模拟器打分取前 64。新算法：

1. 读出层给候选干员算一元分（按房间规格缓存），枚举 `C(beam=18, 容量)` 组合；
2. 取预测前 `shortlist=64`；
3. **追加三类保护候选**：
   - **机制超边**：guide 刊例表里「必须成组上场」的干员集合，按房间规格**精确打分一次**后只留前 16。
     这是阶跃增益，模型学不出来，所以把表本身当静态先验注入。
   - **羁绊闭包**：沿 `named` 边把伙伴拼进组合（例如 `蕾缪安 + 能天使 + 但书`），
     并用一元分补满。旧算法要靠 4960 次枚举「碰巧」撞上，这里用图的边定向提名。
   - **覆盖保障**：候选池里每个干员至少进入一个送审组合。
4. 这批候选**全部送进同一个 `ProductionSimulator`** 打分、排序。

所以模拟器仍是唯一裁判，神经网络只负责「提名」。实测：5/5 房间规格的短名单最优分 =
全量枚举最优分（见基准报告的「短名单质量」一节），而组合数从 4638~4900 降到 74~82。

### 2.5b 初始排班的多起手（解决「同一开关符号相反」）

短名单策略会改变**初始排班**，而逐房间贪心没法给「抢走别的房间更需要的干员」定价。
最典型的是羁绊闭包：它提名的那几个组合在本房间分数更高，但可能吃掉别处更稀缺的干员。

实测（243，同一份模型，只切闭包开关）：

| 场景 | 开闭包 | 关闭包 | 差 |
| --- | --- | --- | --- |
| 243 / 不搓玉 初始分 | 560.2 | **567.5** | 关掉更好 |
| 243 / 不搓玉 最终分 | 598.5 | **607.7** | 关掉更好 |
| 243 / 平衡搓玉 最终分 | **387.6** | 373.1 | 开着更好 |

也就是说这个开关的**符号取决于场景**，没有全局最优的固定值。所以做法是：
两套短名单各生成一套初始排班，用 `optimize()` 真正使用的 `target_selection_score`
当作唯一裁判挑更好的那套（`initial_starts=(12, 0)`）。

代价几乎为零——多几轮 beam 搜索 + 每套一次 `simulator.evaluate`，
实测 243/不搓玉 15.7s vs 单起手 16.0s。收益是把 −11.55 的损失收窄到 −2.39。

### 2.6 三个工程细节

- **技能变体选择**：同一干员在同房型可能有多个技能变体（例如蕾缪安的「订单分发·α」与「相伴」）。
  图模型只对「干员」建模，所以变体选择用规则：**优先选文本点名了同房队友的那个变体**，
  其次按 `score_skill`。这就是 `named` 边在解码阶段的第二个用途。
- **心情/疲劳**：`fatigueRisk` 对同房间干员**可加**，所以不从数据里学，而是精确计算
  `-2 × 时长 × 每小时心情消耗` 加到一元项上。读出层只拟合产能，避免把心情和产能混在同一个
  低维投影里。（不做这一步时，342 场景实测 `fatiguePenalty` 从 -8 恶化到 -43，总分掉 7.5%。）
- **插入搜索预算**：旧算法每轮遍历全部 64 个插入组、最多 8 轮，外加一次纯粹为写审计的
  全量复核扫描——实测 534 次尝试只提分 9 次，却占了 54%~88% 的墙钟时间。
  新算法按图嵌入给插入组排序，只搜索前 48 个、最多 4 轮，未搜索的组显式记为
  `not_searched_graph_budget`（不静默丢弃）。

### 2.7 与父类唯一的行为分歧：纯赤金重复次数

`_apply_pure_gold_drone_cycle_repeats` 的父类规则是「第一个进入容差区间的重复次数就采用」，
不比较综合分。这会造成巨大方差：实测 342/极限搓玉 场景里，重复 2 次只把赤金日差从 -1.58
改善到 -0.11，却把综合分从 388.7 拉到 273.2（-30%），班次从 3 变 6、耗时翻倍。

新优化器改为「**在容差内选综合分最高者**；都不在容差内才沿用父类规则」，
并在 `pureGoldBalancePolicy.selectionRule` 里标注 `max_score_within_tolerance`。
可以用 `GraphOptimizerConfig(prefer_score_within_tolerance=False)` 关掉、回到父类行为。

## 3. 打分模型：社区房型权重

排班分数除了资源流分项（LMD / EXP / 合成玉 / 赤金 / 碎片平衡），还有一条
`roomEfficiency`：把五类房间的**干员增益百分比**按社区通行比例折算到同一货币，
以贸易站为 1 单位。

| 房型 | 权重（贸易 = 1） | 等价读法 |
| --- | --- | --- |
| 贸易站 | 1.0 | 基准 |
| 制造站 | 1.0 | 1% 制造 ≡ 1% 贸易 |
| 发电站 | 0.5 | 2% 发电 ≡ 1% 贸易 |
| 会客室 | 1/12 ≈ 0.0833 | 12% 会客 ≡ 1% 贸易 |
| 办公室 | 2.0 | 1% 办公室 ≡ 2% 贸易 |

实现要点：

* 锚点不是魔法数字，而是从既有常量推出来的：
  `L3 订单 E[lmd]=1450、E[秒]=12204 ⇒ +1% ≈ +102.66 LMD/天 ⇒ ×(1.5/1000) = 0.154 分`。
  换房间等级时这张表仍然自洽，因为权重是**相对**贸易站的。
* 只统计**干员提供**的百分比（不含每槽 1% 的基础值），因为换算表说的是「百分比为干员增益」。
  `ProductionVector.roomSpeedDays` 记录的就是这个量。
* 只有**价值没被资源流覆盖**的三类会进总分：发电（无人机的资源收益只覆盖它真实价值的
  一小部分）、会客（线索/信用完全没有资源项）、办公室（人脉完全没有资源项）。
  贸易/制造已经在 `lmdGross`/`exp`/`orundum` 里计过价，只作为「等价性对照」
  出现在 `roomEfficiencyDetail` 里，不重复计入。
* 房间级选人目标（`room_output_score`）用同一张表，锚点换成房间分口径
  `×0.0036`，所以「2% 发电 ≡ 1% 贸易」在**选人**层面也成立。

243 平衡搓玉实测（无无人机）：`roomEfficiency = 19.31`，其中
发电 4.81 / 会客 0.64 / 办公室 13.86（贸易 34.88、制造 52.12 仅作对照）。

注意这与旧口径的差异：会客室原来按 `meetingSpeed/30` 计（≈0.033 分/%），
新口径 0.0128 分/%——**比原来低 2.6 倍**；办公室原来 ≈0.033 分/%，新口径
0.308 分/%——**高 9 倍**；发电站原来在总分里是 0，新增 0.077 分/%。
旧的 `office` / `meeting` 两条明细保留不动，用于和既有校准口径对比。

## 4. numpy 加速与磁盘缓存

两者都是可选能力，`pyproject.toml` **没有**新增依赖。

* **numpy**：`graph_conv.py` 里 `try: import numpy`，可用时
  ① 图卷积走稠密矩阵路径（`A_r @ H @ W_r`），实测比纯 Python 稀疏传播快 2×；
  ② 岭回归用 `np.linalg.solve`。两条路径**数值等价**（编码器嵌入差 < 1e-17，
  岭回归解差 < 1e-6），测试 `NumpyEquivalenceTest` 守着这一点。
  没有 numpy 时自动回落，功能不变。
* **磁盘缓存**（`graph_cache.py`）：读出层权重 + 机制超边按内容哈希落盘到
  `outputs/graph_model_cache/`，跨进程复用。键里包含图签名、房间规格、拟合超参、
  羁绊基和 `FEATURE_VERSION`，任何一项变了就自动失效。目录不可写时静默降级。
  这对 `recommend` 的进程池路径意义最大——那里每个候选都会新建一个优化器。

## 5. 实测对照

复现命令（默认四个场景，243/333）：

```powershell
python -m arknights_schedule_generator benchmark `
  --roster .\examples\fixtures\yituliu_full_roster_maxed.xlsx `
  --data-dir .\data\cache --output-dir .\outputs\benchmark
```

满练 447 行练度表，同一进程内串行跑两套算法。完整报告在
`outputs/benchmark/graph_vs_hybrid_benchmark.{json,md}`。

（下表的数字由 `benchmark` 命令重新生成，不同机器 / 不同负载下墙钟会有波动，

## 5b. 排班语义的现状：换班 / 宿舍 / 心情 / 办公室

> 基线为 rebase 到 `origin/main` 之后的版本。心情部分在 rebase 之后又改过一轮判定
> （见下面的「换班与宿舍」），早期版本没有心情模型，更早的说法只对旧基线成立。

**换班与宿舍：现在有真正的心情状态机。** `morale.py` 的模型是：
- 心情 0~24；
- **在岗消耗** = 1/h + 技能修正，修正按**作用域**解析（自身 / 当前本站全体 / 控制中枢内 /
  其他设施内 / 全基建），最后 `max(0, ·)`。所以「心情每小时消耗−0.25」真的会降低消耗，
  「当前制造站内所有干员−0.1」会分给同房间的其他人，而不是只算自己；
- **控制中枢**：每名在岗干员让**所有在岗**干员（含中枢自己）消耗 −0.05/h
  （`building_data.controlData.basicCostBuff = -5`），中枢干员自己的技能再叠加
  （`控制中枢内所有干员的心情每小时恢复+0.05` 这类按人数累加，`+1.5` 的线索代价也照实计入）；
- **宿舍恢复** = 白字 `1.5 + 0.1×等级`（`manpowerRecover` 160~200）+ 绿字
  `0.0004 × 氛围`（`comfortManpowerRecoverFactor = 25` ⇒ 1/2500；满氛围按
  `min(5000, 1000×等级)`，L5 正好 +2.0/h）+ 「所有干员 / 自身」两类技能加成
  + 中枢给的「所有宿舍内」加成
  + 单体技能（`除自身以外心情未满的某个干员每小时恢复+N`，26 条）：目标锁定在
  「当前心情最低且未满」的舍友，回满后移交下一个，技能持有者自己永远不是目标；
- **特殊节点（菲亚梅塔「自律」）**：她的恢复「无法获得其他来源」，所以按独立节点算 ——
  只按自身 `+2/h`，不接白字/绿字/舍友技能/中枢宿舍加成，也**不会**成为单体技能的目标；
- **判据是每个干员的收支记账**（`criterion: per_operator_morale_balance`）：一个周期内
  累计「潜在恢复 − 消耗」必须 ≥ 0；
- **硬门槛**：周期 ≤7 天、离岗的人必须在本班宿舍休息、不能同时在岗又在宿舍、
  单周期最低心情 ≥ 0、每人收支 ≥ 0。不满足时 `optimize()` 直接抛 `ValueError`。

为什么判据是收支而不是「周期末心情 ≥ 周期初心情」：24 心情封顶会把落在满心情上的恢复直接丢掉，
于是「休息在前、工作在后」这种完全可持续的排班也会出现末值低于初值。上游旧实现靠「迭代到不动点再比
首尾」绕过这个问题，但封顶让映射不再压缩，迭代 16 步后拿到的既可能是不动点也可能不是，`end_deficit`
就会把可行排班判成不可行；同时不可行排班的 `minimumMorale` 会一路跑到 −180 之类的无意义数字。
现在：
- 判定用闭式收支，与封顶无关，也不再依赖迭代次数（`moraleBalanceDeficitOperators` +
  `failureReasons` 里的 `morale_balance_deficit`）；
- `minimumMorale` / `endingMoraleByOperator` 来自「全员满心情起步走一个周期」的一次确定性重放，
  数值被一个周期的消耗量界定（不会出现 −180 这种重放产物）；可持续周期下它与稳态重放的读数一致，
  不可行排班由上面的收支判据点名，不靠这两个数字下结论；
- `steadyState`（`converged` / `iterations` / `residual`）只是诊断信息，**不参与判定**：
  耦合机制（例如「挑当前心情最低的舍友」这类技能）会让重放一直绕圈却不代表排班不可持续。
- 收支里记的是**潜在恢复**（rate × hours，先不管封顶），所以「满心情时休息」不会被惩罚；
  实际落地的恢复另记在 `appliedRecovery`，两者之差就是封顶浪费。

无法归属的心情条款（按阵营人数、指名干员、`部分设施`、`当与 X` 且 X 不在岗、只对精英干员的宿舍
恢复等）会进 `unmodelledMoraleEffects`，**不静默计 0 也不瞎猜作用域**。真实数据里 21 条命中这一类。

这带来两个必须知道的后果：

1. **5 制造站的布局现在是可行的。** 补上宿舍绿字与控制中枢减耗之前，252/342 的所有组合都会抛
   `ValueError`（缺口只有 −0.6 ~ −3.6 心情/周期）；补上之后满练表上 243/252/342/333 ×
   普通/平衡搓玉 × 2×12/3×8 共 16 种组合**全部可行**，最差收支 +4.0 ~ +30.0（见 handoff §4）。
   基准默认场景仍保留 243/333，只是为了让历史数字可比。
2. 上游会把排班扩成「轮换计划」并重排休息，`cycleHours` 常常是 48 而不是 24。
   这会改变分数口径，也让「纯赤金重复次数」必须遵守 7 天上限——
   新优化器因此显式跳过 `base_cycle_hours × repeat > 168h` 的候选。

**菲亚梅塔：** `自律`（自身 `+2/h` 且「无法获得其他来源提供的心情恢复效果」）按**恢复自给自足的
特殊节点**建模（详见上面「特殊节点」那条）。图侧只在 `graph_features.meta["specialMoraleNodes"]`
里标注，`graph-audit` 的 `specialMoraleNodes` 可见；**不加 GCN 特征**——它只影响心情可行性，
对产能读出层没有梯度，加了反而是噪声，还会让读出层缓存无谓失效。
`患难之交`（`dorm_exchangeAp`，原文「如果自身为满心情，则与当前宿舍**前一位**进驻的干员互换心情」）
按用户要求**不建模「前一位/后一位」**，而是当成一种**手动心情重置**：玩家会特意把她换进宿舍再换出
（随时可以手动调宿舍），所以 `morale._apply_hardship_swaps` 只把「有床位、且自己先够用」的持有者的
**盈余**（`recovery − consumption`）转给全周期最缺心情的干员，`min(盈余, 对方缺口)`；
接收方 `recovery += x`、持有者 `consumption += x`，**转移而不生成**，所以周期总收支不变、
持有者也不会被拖成负数。审计 `version: 4` 起有 `hardshipSwaps` 字段。
已知缺口：解码器的宿舍价值模型还没把「她的盈余可转移」算进去，所以它不会主动为她腾床位
（满练表上四个基准场景里她从未上场，基准数字不受影响）。

**换班节奏：** 仍是**批量固定时刻**。每个 `ShiftPlan` 一个 `start`，同班次所有干员同一刻上下班；
错峰展开只是把计划数乘成 `base × group_count`，时刻沿用同一套网格，没有个体化错峰。

**宿舍分配（M1，已落地）：** 宿舍是**一等分配目标**，不再只是"事后给人配床"。
`_assign_dormitory_quarters` 在心情硬门槛里对**整条排班**跑一次 beam：

- 价值函数手写（宿舍没有产能标签），速率直接来自 `morale.dormitory_recovery_rates` ——
  白字 + 绿字 + 「该宿舍内所有干员」最大值 + 自身加成，自律节点只吃自己的 +2/h，
  单体技能按「本宿舍最缺心情的舍友」近似（一次停留里的总量与实际一致）；
- 两套目标（先补心情缺口 / 先最大化总恢复）+ 旧贪心共三个候选，用心情审计自己的账本
  `(hardGatePassed, 最差收支, 总恢复)` 字典序择优，所以**不会比旧贪心差**；
- 宿舍**不进产能分**：`room_output_score` 没有改动，`score` 与 `scoreBreakdown` 的口径不变
  （16 组扫描与 4 场景基准的分数与 M1 前逐位相同）。
- 性能：beam 只在门槛里跑一次。**不要**把它放回解码的每个班次（`_rebuild_dormitories` 在
  插入/替换搜索里一次 `optimize()` 会调几百次，实测 6× 墙钟而结果完全一样）。
- 收益边界：满练表上心情门槛本来就有 +4.0 以上余量，所以宿舍怎么分都不会改变"谁上场"，
  产能分不会动；M1 的收益是**宿舍账面恢复更高、床位不漏人、分配与审计同口径**。

**电力 → 宿舍等级：** 已建模。`power_status()` 按 `rooms[*].phases[*].electricity` 算供电/耗电，
`--right-side full` 下余量为负时 `auto_adjust_full_power_layout()` 会先砍制造站、再砍宿舍等级，
调整后的 `dormitory_levels` 直接进 `morale` 与宿舍 beam（`_dorm_specs` 用
`levels_or_default(..., 5)` 取等级）。实测 252/342（2 发电站）落到 `(1,1,1,2)`，
恢复率因此是 2.0~2.5/h 而不是 4.0/h。局限：砍电力的**优先级**没有把「宿舍降级 → 恢复率下降」计价；
`guide`/`basic` 预设不做自动调整，252/342 会留下 `feasible=False` 的余量。

**办公室：** 价值已按「1% 办公室 ≡ 2% 贸易站」计入 `roomEfficiency`，
但**选人逻辑仍是按人脉资源解析百分比排序**，不走加权房间分、
也不吃中枢 `control_hire_spd` 加成。这是下一步要处理的地方。

## 6. 已知差距

1. **墙钟时间没有优势，模拟器调用明显减少。** 短名单组装是 Python 层的工作（枚举 + 查表 +
   变体选择），而旧算法的 `itertools.combinations` 和模拟器调用都在 C 层；
   在 4000+ 组合的规模下，纯 Python 的常数因子吃掉了理论上的 60× 优势。
   实测模拟器调用降到 0.54~0.77 倍，但墙钟约 1.0~1.2 倍。
   后续若把读出层的前向搬到 numpy（或直接把短名单缓存成「房间规格 → 组合列表」的持久表），
   墙钟才会真正下降。
2. **合成玉贸易站的零梯度问题已修（O_DIAMOND 校准 v2，2026-11）。**
   旧实现里 `production.guide_orundum_trade_lookup` 对**任何** L3 `O_DIAMOND` 房间都命中，
   把速度覆盖成常数 `132%`，干员技能完全不参与（4750 个组合的 orundum **全是 282.000**，
   读出层 holdout R² = **−110.6**）。现在的口径：
   速度只来自在岗干员技能、**不裁剪订单上限**（源石碎片供给才是真约束，裁剪还会把
   +32% 以上的梯度全部压平）、再用单一常数 `ORUNDUM_ORDER_THROUGHPUT_SCALE` 把量级锚在
   「L3 / 3 工位 / +132% / 12h ⇒ 282.000」上。
   结果：同一批 4750 个组合铺开到 **123.6 ~ 339.6**，同一房间的 holdout **R² = 0.753**、
   Spearman 0.94（`outputs/benchmark_orundumv2/`）。
   这条会把搓玉类基准的整体分数抬高（详见 §5 与 handoff §5），**混合与图卷积同口径**，比较仍公平。
   改这个常数要同时改 `tools/measure_orundum_anchor.py` 的验收与两张基准表。
3. **阶跃型羁绊只能靠注入，不能靠学。** 16 行龙门币刊例表、3 行制造刊例表是硬编码先验，
   新干员/新机制出现时需要同步维护那张表——这一点旧算法同样依赖。
4. **插入搜索的预算是有损的。** 预算 48 组 / 4 轮相比父类的 64 组 / 8 轮会漏掉排在后半段的
   插入机会。实测它虽然更快，但最终分数对插入顺序高度敏感（同一批场景里波动 ±3%），
   所以**默认关闭**，只在 `limit_insertion_search=True` 时启用。
5. **同分组合的先后不再是主导因素，但短名单仍会漏人。** v2 之前 L3 合成玉贸易站 4750 个组合
   全是 282.0，谁进前 64 全看排序（±3%）；现在有真梯度，这项风险显著下降
   （O_DIAMOND 的 top16 召回 1.0 → 0.75，是「同一批最优组合并列更多」造成的，不是覆盖缺口：
   全量最优仍然是短名单最优）。**新的已知缺口**是：技能变体表按**无排除**候选池建立，
   排除一批干员后可能出现「短名单里没人能填满这间房」，把房间填成 1~2 人。
   v2 之前这被 O_DIAMOND 的常数标签掩盖（空房间也满产），现在会直接掉分
   （333 平衡搓玉 3×8 实测 −144 分）。已加兜底：`_room_combos` 在
   `0 < len(names) < capacity` 时退回父类全量枚举；`names` 为空时仍返回空短名单，
   让调用方的逐人贪心把房间填满（实测后者在 342 不搓玉上更好）。
6. **拟合样本数不是越大越好。** 288 → 1536 样本让 holdout R² 从 0.82 升到 0.89、
   MAE 从 2.4 降到 1.5，但最终排班分数系统性下降约 4%：模型越锐利，短名单越集中在
   同一批干员上，下游搜索失去多样性。所以默认仍是 288。
7. **错峰展开的周期长度是阶跃成本，必须显式管。** 心情硬门槛不过时，`_ensure_sustainable_morale_cycle`
   会按 `groupCount = ceil(staggerWeight / staggerCapacity)` 把排班展开成 `groupCount` 组，
   周期 = Σ班次时长 × 组数。而 `fastRotationRooms`（有干员带「心情每小时消耗 +N」的房间）
   的席位是**整块**从错峰容量里扣掉的，所以「会客室里放一个 +2.0/h 的干员」这种小事，
   能把 `staggerCapacity` 从 12 压到 7、把 48h 周期逼成 72h —— **日均分直接除以 3**。
   实测（O_DIAMOND 校准 v2 之后的 333 平衡搓玉 3×8）：图卷积的初始排班给会客室放了见行者，
   周期 72h，分数 434.5；混合算法用 48h，514.6。现在 `_relieve_morale_rotation_pressure`
   在展开前做一次定向修复：把带 +消耗 的干员换成本房间次优的非消耗干员，**只在确实减少组数时**
   才保留改动（换不满一屋人就放弃；换完还要重过「相邻班次不重复」的约束）。
   这条把同一场景拉到 492.6（−4.28%），并且让 243 不搓玉 3×8 的周期也从 72h 回到 48h。
   **局限**：修复只处理「换一个人就能降组数」的情形；如果穷举后仍然需要 3 组，模型不会
   重新分配房间，也不会给「周期长度」定价 —— 这属于 handoff §3 第 3 步（轮转表）的范围。
8. **「不搓玉稳输」的旧推断已被证伪两次。** 第一次是 M1（宿舍一等分配）：四场景分数逐位相同。
   第二次是 O_DIAMOND 校准 v2：342 不搓玉从 −3.09% 变成 **+0.17%** ——
   那个「稳输」里有一部分其实就是零梯度房间造成的（§6 第 2 条），不是「逐房吃人」。
10. **M3c（跨房间/跨班次联合解码）：试过一版，被候选池结构挡住。**
    做法是把「班次 × 房间」排成一条序列做一次 beam，状态里滚动
    `(第 0 班名单, 上一班名单, 本班已用名单)`，让所有班次一起竞争同一批干员。
    结果**必然死路**：候选表只能来自**无排除**短名单，而短名单的候选池上限是
    `COMBO_CANDIDATE_POOL_LIMIT = 32` 人；第 0 班一共占 29 席，于是第 1 班的
    `trading_1` 连一个「三人都不冲突」的组合都找不到（放宽到全量 129~162 条候选也一样）。
    逐班次解码之所以不死，是因为它把上一班名单塞进 `_room_combos(excluded=…)`，
    **池子会按排除集重建**（前 32 名之外的干员才会进来）。要继续就得逐状态重算短名单，
    单次 10~20ms × beam 256 → 每个死路房间 2.5~5s，不划算。
    记录在 handoff §3 第 6 步 M3c；另外注意 `_build_shifts` 是**父类**方法，
    任何跨班次联合解码都会同时抬高混合与图卷积两列，不会自动缩小差距。
9. **剩下的不搓玉差距才是「逐房吃人」——已量到具体名次，且证明不是候选/beam 的问题。**
   `tools/probe_m3a_ranks.py` 对 243 不搓玉 / 342 不搓玉 / 333 平衡搓玉 3×8 统计「解码选中的组合
   落在自己精确排名的第几名」：`min 0 / median 1 / max 63`，最差的那几条正好卡在
   `JOINT_PRODUCTION_CANDIDATE_LIMIT = 64` 的边界上——**前面 60 多条全是「同班已用」的冲突组合**。
   顺手排除了两个看起来最像原因的旋钮：候选条数 64→192（分数一格不动、墙钟 ×2）、
   联合 beam 宽度 256→1024→4096（同样一格不动、墙钟 15→22s / 72→110s）。
   所以 shortlist 的**排序**没问题、**数量**也不是瓶颈，瓶颈是「谁去哪间房要一起决定」。
   历史上（校准 v1 时代）的逐房间差分如下： 逐房间差分（校准 v1 时代的 342 不搓玉）：
   −21.06 分里 −20.4 来自生产房间的精确分，其中贸易站占 −17.3；`exp` 三个场景里
   只在 252 差 420、会客室完全一样、办公室折算只值 0.77 分。机制是：短名单**覆盖**没问题
   （61.645 就在 `TRADING/O_GOLD` 短名单第 1 名，top16 召回 1.0），但 beam **按读出层预测分
   逐房吃人**，前一个房间把 top 组合的成员拿走后，后面的房间只能吃到**自己短名单第 56 名**
   的 44.72（342 的 `trading_2`）。混合算法是穷举 + 跨房间的插入/替换，所以能保住
   「需要三个指定干员」的组合。校准 v2 之后同一现象出现在 O_DIAMOND 上（333 平衡搓玉 3×8：
   图卷积把最强三人组 202.4 放进一个班次，另外两个班次只剩 118.4/154.4）。
   **修法见 handoff §3 第 6 步（M3）：房间节点 ↔ 干员节点匹配，
   第一步是短名单 top-K 用精确分重排。**
