# 图卷积优化器：数据审计、算法与实测对照

本文记录把房间组合搜索从「全量枚举 + 混合局部搜索」换成「静态图卷积短名单 + 精确复核」的
决策依据、实现细节和实测结果。

---

## 1. 仓库里到底有没有足够的静态图信息？

结论：**结构信息足够，数值强度不足**。所以做法是「用图给出结构先验，用现有生产模拟器当老师
标定数值」。

用 `graph-audit` 在本地 `data/cache`（`Stream://torappu-data/v074/rel74.0`，734 个 buff，
418 个可进基建的干员）和示例满练表（447 行 → 合并同名后 438 名干员）上实测：

| 项目 | 数值 | 来源 |
| --- | --- | --- |
| 干员节点 | 438 | 练度表 × `character_table.json` |
| 特征宽度 | 24 | 见 §2.1 |
| 阵营/势力组 | 55 | `character_table.json` 的 `nationId` / `groupId` / `teamId`（含 `mainPower` / `subPower`），经 `data.py:faction_tags_for_char` 归一化 |
| 阵营边 | 13584 | 同组两两相连，权重按组规模衰减 |
| 点名羁绊边 | 72（36 对） | 技能文本里点了另一位干员的名字 |
| 组合机制边 | 2252 | 技能文本命中「当与 / 同一个贸易站 / 归零 / 低语 / 特别订单 / 高价值订单 / 回收利用 / 仓库容量 …」 |
| 孤立干员 | 36 | 35 名「支援机械」/剧情干员，无阵营无队友，对排班无羁绊影响 |

### 1.1 真实存在的「羁绊」有四类，不是一张成对权重表

读 `production.py` / `skill_rules.py` 后确认，游戏里生效的协同只有这四种形态：

1. **阵营计数型**：`skill_rules.py:342-451` 的 13 条硬编码分支，公式形如
   `+20 × 本房间 glasgow 人数`、`+3 × min(全基建 rhine 人数, 5)`。
   → 图上就是**阵营超节点 + 求和聚合**，这是图卷积最自然能表达的东西。
2. **点名干员型**：`凛御银灰`、`能天使`、`推进之王/维娜·维多利亚`、`古米`、`阿米娅` 等字面量。
   → 图上就是 `named` 边。实测 36 对，包括 `德克萨斯 ↔ 拉普兰德`、`蕾缪安 ↔ 能天使`、
   `烈夏 ↔ 古米`、`维希戴尔 ↔ 伊内丝/赫德雷`。
3. **阶跃查表型**：`production.py:64-315` 的 guide 刊例表——16 行龙门币贸易、1 行合成玉贸易、
   3 行制造。命中即**用刊例值覆盖**干员技能计算（`evaluate_trading` / `evaluate_manufacture`），
   所以这是**阶跃函数**，线性读出层学不出来。例如但书 + 两名 45% 伙伴 → 200%，
   巫恋 + 龙舌兰 + 但书 → 207%。
4. **同房间条件文本型**：`当与X在同一个贸易站时…`，由 `skill_rules.py:284-301` 正则匹配。

### 1.2 缺口：数值强度不在数据里

- `buff.efficiency` 对绝大多数技能是 0，真实数值藏在 `description` 文本里，
  由 `data.py:parse_skill_score` 取「描述里最大的 `+N%`」。这是粗糙的一阶近似。
- 阵营计数、阶跃查表、心情消耗这些**条件与非线性**，是代码里的硬编码逻辑，不是数据字段。

所以新优化器**不自己定义收益**：它把 `ProductionSimulator` 当作老师，用它的输出拟合读出层。
换句话说，图提供结构归纳偏置，模拟器提供数值监督。

## 2. 算法

### 2.1 节点特征（`graph_features.py`，24 维，全部确定、可复现）

| 组 | 维度 | 内容 |
| --- | --- | --- |
| 练度 | 6 | 星级、精英化、等级、潜能、技能等级、最高专精 |
| 房型能力 | 7 | 各房型的最强 `parsed_score` / 归一化常数 |
| 产物亲和 | 5 | `O_GOLD` / `O_DIAMOND` / `F_GOLD` / `F_EXP` / `F_DIAMOND` |
| 结构标记 | 6 | 复杂条件比例、是否有未解锁技能、阵营数、点名度数、组合机制标记、guide 锚点 |

编码器会额外拼上 7 个房型能力的平方项（共 31 维输入），让线性读出层能表达产能饱和的凹性。

### 2.2 三类边与阵营超节点

- `faction`：同组两两相连，权重 `1/log2(2+组规模)`，超过 60 人的阵营（`rhodes` 94 人）**不建边**，
  否则整张图退化成全连接、小团体的信号被稀释。
- `named`：技能文本点名 → 双向边，权重 1.5。
- `combo`：命中组合机制 → 只在**该技能所属房型内**连接，权重 0.4。

传播时 `faction` 不走 O(n²) 边表，而是**超节点均值**：
每个阵营组先算组内均值，再对干员取其所属组的均值。数学上等价于完全子图的行归一化聚合，
复杂度从 O(组²) 降到 O(节点数)；`rhodes` 这种大组也不会变成全连接。

### 2.3 固定超参图卷积（`graph_conv.py`）

```
h'[i] = act( ws·W_self·h[i] + Σ_r wr·W_r·(A_r h)[i] )
```

- `W_*` 是**确定性稀疏随机投影**（SplitMix64 播种，每通道 3 个非零）。所以前向传播跨平台、
  跨进程、跨运行完全一致；没有训练循环、没有 torch/numpy 依赖、不需要 GPU。
  这是 Gaussian random feature 的思路：随机投影负责把结构摊开，学习只发生在最后一层。
- 关系权重固定：`faction 0.55 / named 1.30 / combo 0.45`（羁绊比阵营更具体，给更高的权重）。
- 嵌入 = 原始特征 ⊕ 每层隐表示，默认 `31 + 2×8 = 47` 维。

### 2.4 闭式读出层：一元 + 二元协同

对房间组合 `S`：

```
ŷ(S) = b + Σ_{i∈S} w_u·e_i + Σ_{i<j∈S} w_p·(e_i ⊙ e_j) + 房间项
```

这正是「单人贡献 + 两人同房才生效的增益」的结构。权重用**岭回归正规方程 + 高斯-约当消元**
闭式求解（47 维嵌入 → 99 个参数，毫秒级），无需梯度下降。

训练标签来自 `ScheduleOptimizer._score_room_combo`（即模拟器的房间分数），采样 288 个
1~满编的组合。实测 holdout 质量：

| 房间 | 目标 | R²(holdout) | MAE | MAE/均值 | Spearman |
| --- | --- | --- | --- | --- | --- |
| TRADING | O_GOLD | 0.82 | 2.38 | 7.5% | 0.91 |
| TRADING | O_DIAMOND | — | 18.53 | 6.6% | 0.30 |
| MANUFACTURE | F_EXP | 0.71 | 1.68 | 6.7% | 0.88 |
| MANUFACTURE | F_GOLD | 0.57 | 6.35 | 5.0% | 0.90 |
| MANUFACTURE | F_DIAMOND | 0.75 | 3.58 | 4.7% | 0.97 |

`O_DIAMOND` 的 R² 无意义：guide 刊例把 L3 合成玉贸易站固定成 132%，标签几乎是常数
（方差 12 对均值 282）。代码会检测这种情况并退化成常数模型。

### 2.5 从「全量枚举」到「短名单 + 精确复核」

旧算法对一个房间做 `C(32,3)=4960` 次模拟器打分取前 64。新算法：

1. 读出层给候选干员算一元分（按房间规格缓存），枚举 `C(beam=18, 容量)` 组合；
2. 取预测前 `shortlist=64`；
3. **追加三类保护候选**：
   - **机制超边**：guide 刊例表里「必须成组上场」的干员集合，按房间规格**精确打分一次**后只留前 16。
     这是阶跃增益，模型学不出来，所以把表本身当静态先验注入。
   - **羁绊闭包**：沿 `named` 边把伙伴拼进组合（例如 `蕾缪安 + 能天使 + 但书`），
     并用一元分补满。旧算法要靠 4960 次枚举「碰巧」撞上，这里用图的边定向提名。
   - **覆盖保障**：候选池里每个干员至少进入一个送审组合。
4. 这批候选**全部送进同一个 `ProductionSimulator`** 打分、排序。

所以模拟器仍是唯一裁判，神经网络只负责「提名」。实测：5/5 房间规格的短名单最优分 =
全量枚举最优分（见基准报告的「短名单质量」一节），而组合数从 4638~4900 降到 74~82。

### 2.6 三个工程细节

- **技能变体选择**：同一干员在同房型可能有多个技能变体（例如蕾缪安的「订单分发·α」与「相伴」）。
  图模型只对「干员」建模，所以变体选择用规则：**优先选文本点名了同房队友的那个变体**，
  其次按 `score_skill`。这就是 `named` 边在解码阶段的第二个用途。
- **心情/疲劳**：`fatigueRisk` 对同房间干员**可加**，所以不从数据里学，而是精确计算
  `-2 × 时长 × 每小时心情消耗` 加到一元项上。读出层只拟合产能，避免把心情和产能混在同一个
  低维投影里。（不做这一步时，342 场景实测 `fatiguePenalty` 从 -8 恶化到 -43，总分掉 7.5%。）
- **插入搜索预算**：旧算法每轮遍历全部 64 个插入组、最多 8 轮，外加一次纯粹为写审计的
  全量复核扫描——实测 534 次尝试只提分 9 次，却占了 54%~88% 的墙钟时间。
  新算法按图嵌入给插入组排序，只搜索前 48 个、最多 4 轮，未搜索的组显式记为
  `not_searched_graph_budget`（不静默丢弃）。

### 2.7 与父类唯一的行为分歧：纯赤金重复次数

`_apply_pure_gold_drone_cycle_repeats` 的父类规则是「第一个进入容差区间的重复次数就采用」，
不比较综合分。这会造成巨大方差：实测 342/极限搓玉 场景里，重复 2 次只把赤金日差从 -1.58
改善到 -0.11，却把综合分从 388.7 拉到 273.2（-30%），班次从 3 变 6、耗时翻倍。

新优化器改为「**在容差内选综合分最高者**；都不在容差内才沿用父类规则」，
并在 `pureGoldBalancePolicy.selectionRule` 里标注 `max_score_within_tolerance`。
可以用 `GraphOptimizerConfig(prefer_score_within_tolerance=False)` 关掉、回到父类行为。

## 3. 实测对照

复现命令：

```powershell
python -m arknights_schedule_generator benchmark `
  --roster .\examples\fixtures\yituliu_full_roster_maxed.xlsx `
  --data-dir .\data\cache --output-dir .\outputs\benchmark
```

满练 447 行练度表，同一进程内串行跑两套算法。完整报告在
`outputs/benchmark/graph_vs_hybrid_benchmark.{json,md}`。

（下表的数字由 `benchmark` 命令重新生成，不同机器 / 不同负载下墙钟会有波动，
以「模拟器调用比」这个算法层面的确定性成本为准。）

| 场景 | 混合搜索分 | 图卷积分 | 分数变化 | 混合耗时 | 图卷积耗时 | 模拟器调用比 |
| --- | --- | --- | --- | --- | --- | --- |
| 243 / 平衡搓玉 / 2×12h / 无无人机 | 362.613 | **367.050** | **+1.22%** | 21.87s | 15.88s | 0.542× |
| 252 / 平衡搓玉 / 3×8h / 无人机 auto | 449.300 | **463.093** | **+3.07%** | 102.81s | 98.33s | 0.707× |
| 342 / 极限搓玉 / 3×8h / 无人机 auto | 431.226 | **451.987** | **+4.81%** | 41.89s | 58.51s | 0.768× |

汇总：**3 胜 0 负 0 平**，平均分数比 **1.030**（+3.0%），平均墙钟比 1.026（基本持平），
平均模拟器调用比 **0.672**（少 33%）。

短名单质量（同一模拟器下与全量枚举对比）：

| 房间 | 目标 | 全量组合数 | 短名单组合数 | 全量最优 | 短名单最优 | 命中 |
| --- | --- | --- | --- | --- | --- | --- |
| TRADING | O_GOLD | 4638 | 75 | 61.645 | 61.645 | 是 |
| TRADING | O_DIAMOND | 4750 | 74 | 282.000 | 282.000 | 是 |
| MANUFACTURE | F_EXP | 4724 | 75 | 38.880 | 38.880 | 是 |
| MANUFACTURE | F_DIAMOND | 4900 | 80 | 99.840 | 99.840 | 是 |
| MANUFACTURE | F_GOLD | 4900 | 82 | 158.400 | 158.400 | 是 |

即：把每个房间的候选组合从 ~4800 个压到 ~80 个，**最优分完全不变**。
分数之所以还能提升，是因为插入搜索的组顺序变了（按图先验排序），
于是找到了旧算法没走到的高分组合——例如 243 平衡搓玉 B 班贸易站从 45.864 提到 48.597。

## 4. 已知差距

1. **墙钟时间没有优势，模拟器调用明显减少。** 短名单组装是 Python 层的工作（枚举 + 查表 +
   变体选择），而旧算法的 `itertools.combinations` 和模拟器调用都在 C 层；
   在 4000+ 组合的规模下，纯 Python 的常数因子吃掉了理论上的 60× 优势。
   实测模拟器调用降到 0.54~0.77 倍，但墙钟约 1.0~1.2 倍。
   后续若把读出层的前向搬到 numpy（或直接把短名单缓存成「房间规格 → 组合列表」的持久表），
   墙钟才会真正下降。
2. **合成玉贸易站是零梯度房间。** guide 刊例把 L3 合成玉贸易站固定成 132%，与干员无关，
   所以模型对它只能给常数，选择等于随机。这不影响总分（任何组合分数相同），
   但意味着图模型对该房间没有实际贡献。
3. **阶跃型羁绊只能靠注入，不能靠学。** 16 行龙门币刊例表、3 行制造刊例表是硬编码先验，
   新干员/新机制出现时需要同步维护那张表——这一点旧算法同样依赖。
4. **插入搜索的预算是有损的。** 预算 48 组 / 4 轮相比父类的 64 组 / 8 轮会漏掉排在后半段的
   插入机会；实测在满练表上分数不降反升，但这是经验值，不是理论保证。

| 文件 | 职责 |
| --- | --- |
| `arknights_schedule_generator/graph_features.py` | 静态图构建 + `graph-audit` 体检报告 |

CLI：

```powershell
# 只要静态图体检
python -m arknights_schedule_generator graph-audit --roster <练度表> --data-dir data/cache

# 用图卷积优化器生成排班
python -m arknights_schedule_generator generate --roster <练度表> --layout 243 `
  --mode balanced-orundum --optimizer graph --output outputs/schedule_graph.json

# 新旧对照
python -m arknights_schedule_generator benchmark --roster <练度表> --output-dir outputs/benchmark
```
