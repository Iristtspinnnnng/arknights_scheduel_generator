# 图卷积优化器：数据审计、算法与实测对照

本文记录把房间组合搜索从「全量枚举 + 混合局部搜索」换成「静态图卷积短名单 + 精确复核」的
决策依据、实现细节和实测结果。

---

## 1. 仓库里到底有没有足够的静态图信息？

结论：**结构信息足够，数值强度不足**。所以做法是「用图给出结构先验，用现有生产模拟器当老师
标定数值」。

用 `graph-audit` 在本地 `data/cache`（`Stream://torappu-data/v074/rel74.0`，734 个 buff，
418 个可进基建的干员）和示例满练表（447 行 → 合并同名后 438 名干员）上实测：

| 项目 | 数值 | 来源 |
| --- | --- | --- |
| 干员节点 | 438 | 练度表 × `character_table.json` |
| 特征宽度 | 24 | 见 §2.1 |
| 阵营/势力组 | 55 | `character_table.json` 的 `nationId` / `groupId` / `teamId`（含 `mainPower` / `subPower`），经 `data.py:faction_tags_for_char` 归一化 |
| 阵营边 | 13584 | 同组两两相连，权重按组规模衰减 |
| 点名羁绊边 | 72（36 对） | 技能文本里点了另一位干员的名字 |
| 组合机制边 | 2252 | 技能文本命中「当与 / 同一个贸易站 / 归零 / 低语 / 特别订单 / 高价值订单 / 回收利用 / 仓库容量 …」 |
| 孤立干员 | 36 | 35 名「支援机械」/剧情干员，无阵营无队友，对排班无羁绊影响 |

### 1.1 真实存在的「羁绊」有四类，不是一张成对权重表

读 `production.py` / `skill_rules.py` 后确认，游戏里生效的协同只有这四种形态：

1. **阵营计数型**：`skill_rules.py:342-451` 的 13 条硬编码分支，公式形如
   `+20 × 本房间 glasgow 人数`、`+3 × min(全基建 rhine 人数, 5)`。
   → 图上就是**阵营超节点 + 求和聚合**，这是图卷积最自然能表达的东西。
2. **点名干员型**：`凛御银灰`、`能天使`、`推进之王/维娜·维多利亚`、`古米`、`阿米娅` 等字面量。
   → 图上就是 `named` 边。实测 36 对，包括 `德克萨斯 ↔ 拉普兰德`、`蕾缪安 ↔ 能天使`、
   `烈夏 ↔ 古米`、`维希戴尔 ↔ 伊内丝/赫德雷`。
3. **阶跃查表型**：`production.py:64-315` 的 guide 刊例表——16 行龙门币贸易、1 行合成玉贸易、
   3 行制造。命中即**用刊例值覆盖**干员技能计算（`evaluate_trading` / `evaluate_manufacture`），
   所以这是**阶跃函数**，线性读出层学不出来。例如但书 + 两名 45% 伙伴 → 200%，
   巫恋 + 龙舌兰 + 但书 → 207%。
4. **同房间条件文本型**：`当与X在同一个贸易站时…`，由 `skill_rules.py:284-301` 正则匹配。

### 1.2 缺口：数值强度不在数据里

- `buff.efficiency` 对绝大多数技能是 0，真实数值藏在 `description` 文本里，
  由 `data.py:parse_skill_score` 取「描述里最大的 `+N%`」。这是粗糙的一阶近似。
- 阵营计数、阶跃查表、心情消耗这些**条件与非线性**，是代码里的硬编码逻辑，不是数据字段。

所以新优化器**不自己定义收益**：它把 `ProductionSimulator` 当作老师，用它的输出拟合读出层。
换句话说，图提供结构归纳偏置，模拟器提供数值监督。

## 2. 算法

### 2.1 节点特征（`graph_features.py`，24 维，全部确定、可复现）

| 组 | 维度 | 内容 |
| --- | --- | --- |
| 练度 | 6 | 星级、精英化、等级、潜能、技能等级、最高专精 |
| 房型能力 | 7 | 各房型的最强 `parsed_score` / 归一化常数 |
| 产物亲和 | 5 | `O_GOLD` / `O_DIAMOND` / `F_GOLD` / `F_EXP` / `F_DIAMOND` |
| 结构标记 | 6 | 复杂条件比例、是否有未解锁技能、阵营数、点名度数、组合机制标记、guide 锚点 |

编码器会额外拼上 7 个房型能力的平方项（共 31 维输入），让线性读出层能表达产能饱和的凹性。

### 2.2 三类边与阵营超节点

- `faction`：同组两两相连，权重 `1/log2(2+组规模)`，超过 60 人的阵营（`rhodes` 94 人）**不建边**，
  否则整张图退化成全连接、小团体的信号被稀释。
- `named`：技能文本点名 → 双向边，权重 1.5。
- `combo`：命中组合机制 → 只在**该技能所属房型内**连接，权重 0.4。

传播时 `faction` 不走 O(n²) 边表，而是**超节点均值**：
每个阵营组先算组内均值，再对干员取其所属组的均值。数学上等价于完全子图的行归一化聚合，
复杂度从 O(组²) 降到 O(节点数)；`rhodes` 这种大组也不会变成全连接。

### 2.3 固定超参图卷积（`graph_conv.py`）

```
h'[i] = act( ws·W_self·h[i] + Σ_r wr·W_r·(A_r h)[i] )
```

- `W_*` 是**确定性稀疏随机投影**（SplitMix64 播种，每通道 3 个非零）。所以前向传播跨平台、
  跨进程、跨运行完全一致；没有训练循环、没有 torch/numpy 依赖、不需要 GPU。
  这是 Gaussian random feature 的思路：随机投影负责把结构摊开，学习只发生在最后一层。
- 关系权重固定：`faction 0.55 / named 1.30 / combo 0.45`（羁绊比阵营更具体，给更高的权重）。
- 嵌入 = 原始特征 ⊕ 每层隐表示，默认 `31 + 2×8 = 47` 维。

### 2.4 闭式读出层：一元 + 二元协同

对房间组合 `S`：

```
ŷ(S) = b + Σ_{i∈S} w_u·e_i + Σ_{i<j∈S} w_p·(e_i ⊙ e_j) + 房间项
```

这正是「单人贡献 + 两人同房才生效的增益」的结构。权重用**岭回归正规方程 + 高斯-约当消元**
闭式求解（47 维嵌入 → 99 个参数，毫秒级），无需梯度下降。

训练标签来自 `ScheduleOptimizer._score_room_combo`（即模拟器的房间分数），采样 288 个
1~满编的组合。实测 holdout 质量：

| 房间 | 目标 | R²(holdout) | MAE | MAE/均值 | Spearman |
| --- | --- | --- | --- | --- | --- |
| TRADING | O_GOLD | 0.865 | 2.00 | 6.3% | 0.95 |
| TRADING | O_DIAMOND | — | 18.52 | 6.6% | 0.30 |
| MANUFACTURE | F_EXP | 0.696 | 1.72 | 6.9% | 0.86 |
| MANUFACTURE | F_GOLD | 0.571 | 6.35 | 5.0% | 0.90 |
| MANUFACTURE | F_DIAMOND | 0.755 | 3.58 | 4.7% | 0.97 |

`O_DIAMOND` 的 R² 无意义：guide 刊例把 L3 合成玉贸易站固定成 132%，标签几乎是常数
（方差 12 对均值 282）。代码会检测这种情况并退化成常数模型。

### 2.4b 显式羁绊基：把「羁绊值多少分」写出来

图卷积只给**结构**，数值强度靠 47 维嵌入去凑——这不够，因为游戏里两种羁绊
本来就是**可加 / 可配对**的：

* 阵营计数型（`+20 × 本房 glasgow 人数`）对同房干员可加 → 塞进**一元项**；
* 点名羁绊型（`当与德克萨斯在同一个贸易站时…`）只在两人同房时生效 → 塞进**二元项**。

所以读出层的基扩成两段：图嵌入基 + 显式羁绊基（`graph_bonds.py`）。
系数由岭回归闭式解出，可以直接读（注意：这些阵营列彼此相关性高，岭回归会把权重
分摊到同族标签上，所以**绝对值只有排名意义**，不要逐条当成游戏内真实公式）：

| 房间 / 目标 | 特征 | 学到的系数 |
| --- | --- | --- |
| TRADING / O_GOLD | `faction_count:victoria` | +9.63 分 / 人 |
| TRADING / O_GOLD | `faction_count:laterano` | +8.41 分 / 人 |
| TRADING / O_GOLD | `bond:A_mentions_B`（A 点名 B） | +1.77 分 / 对 |

三个关键取舍（都是实测出来的，不是猜的）：

1. **必须按「房间 × 产物」筛选**。黑钢（`+2 × min(全基建黑钢人数,3)`）和莱茵用的是
   **全基建**计数、机械精通用**发电站**计数，把它们当成房间级一元项只会加噪声——
   实测制造站 holdout R² 从 0.75 掉到 0.70。现在只有
   `IN_ROOM_COUNT_TAGS` 里语义成立的组合才开（贸易: glasgow/laterano/mh2；
   制造 F_EXP: A1/ussg；发电: op/laterano）。
2. **别名标签要按成员集合去重**（`rhine`/`rh`、`blacksteel`/`bs`、`knight`/`kazimierz`），
   否则列完全共线，岭回归既不稳也没法解释。
3. **羁绊基要单独加强收缩**（`bond_ridge_scale=4`）：列少、样本少，用列缩放
   把它的有效惩罚放大 4 倍。

效果（贸易站 O_GOLD，最重要的房间）：R² 0.8206 → **0.8649**，
MAE 2.382 → **1.997**，Spearman 0.907 → **0.950**。制造站基本中性（±1pp），
因为它们的阵营机制本来就不是房间内计数。

### 2.5 从「全量枚举」到「短名单 + 精确复核」

旧算法对一个房间做 `C(32,3)=4960` 次模拟器打分取前 64。新算法：

1. 读出层给候选干员算一元分（按房间规格缓存），枚举 `C(beam=18, 容量)` 组合；
2. 取预测前 `shortlist=64`；
3. **追加三类保护候选**：
   - **机制超边**：guide 刊例表里「必须成组上场」的干员集合，按房间规格**精确打分一次**后只留前 16。
     这是阶跃增益，模型学不出来，所以把表本身当静态先验注入。
   - **羁绊闭包**：沿 `named` 边把伙伴拼进组合（例如 `蕾缪安 + 能天使 + 但书`），
     并用一元分补满。旧算法要靠 4960 次枚举「碰巧」撞上，这里用图的边定向提名。
   - **覆盖保障**：候选池里每个干员至少进入一个送审组合。
4. 这批候选**全部送进同一个 `ProductionSimulator`** 打分、排序。

所以模拟器仍是唯一裁判，神经网络只负责「提名」。实测：5/5 房间规格的短名单最优分 =
全量枚举最优分（见基准报告的「短名单质量」一节），而组合数从 4638~4900 降到 74~82。

### 2.5b 初始排班的多起手（解决「同一开关符号相反」）

短名单策略会改变**初始排班**，而逐房间贪心没法给「抢走别的房间更需要的干员」定价。
最典型的是羁绊闭包：它提名的那几个组合在本房间分数更高，但可能吃掉别处更稀缺的干员。

实测（243，同一份模型，只切闭包开关）：

| 场景 | 开闭包 | 关闭包 | 差 |
| --- | --- | --- | --- |
| 243 / 不搓玉 初始分 | 560.2 | **567.5** | 关掉更好 |
| 243 / 不搓玉 最终分 | 598.5 | **607.7** | 关掉更好 |
| 243 / 平衡搓玉 最终分 | **387.6** | 373.1 | 开着更好 |

也就是说这个开关的**符号取决于场景**，没有全局最优的固定值。所以做法是：
两套短名单各生成一套初始排班，用 `optimize()` 真正使用的 `target_selection_score`
当作唯一裁判挑更好的那套（`initial_starts=(12, 0)`）。

代价几乎为零——多几轮 beam 搜索 + 每套一次 `simulator.evaluate`，
实测 243/不搓玉 15.7s vs 单起手 16.0s。收益是把 −11.55 的损失收窄到 −2.39。

### 2.6 三个工程细节

- **技能变体选择**：同一干员在同房型可能有多个技能变体（例如蕾缪安的「订单分发·α」与「相伴」）。
  图模型只对「干员」建模，所以变体选择用规则：**优先选文本点名了同房队友的那个变体**，
  其次按 `score_skill`。这就是 `named` 边在解码阶段的第二个用途。
- **心情/疲劳**：`fatigueRisk` 对同房间干员**可加**，所以不从数据里学，而是精确计算
  `-2 × 时长 × 每小时心情消耗` 加到一元项上。读出层只拟合产能，避免把心情和产能混在同一个
  低维投影里。（不做这一步时，342 场景实测 `fatiguePenalty` 从 -8 恶化到 -43，总分掉 7.5%。）
- **插入搜索预算**：旧算法每轮遍历全部 64 个插入组、最多 8 轮，外加一次纯粹为写审计的
  全量复核扫描——实测 534 次尝试只提分 9 次，却占了 54%~88% 的墙钟时间。
  新算法按图嵌入给插入组排序，只搜索前 48 个、最多 4 轮，未搜索的组显式记为
  `not_searched_graph_budget`（不静默丢弃）。

### 2.7 与父类唯一的行为分歧：纯赤金重复次数

`_apply_pure_gold_drone_cycle_repeats` 的父类规则是「第一个进入容差区间的重复次数就采用」，
不比较综合分。这会造成巨大方差：实测 342/极限搓玉 场景里，重复 2 次只把赤金日差从 -1.58
改善到 -0.11，却把综合分从 388.7 拉到 273.2（-30%），班次从 3 变 6、耗时翻倍。

新优化器改为「**在容差内选综合分最高者**；都不在容差内才沿用父类规则」，
并在 `pureGoldBalancePolicy.selectionRule` 里标注 `max_score_within_tolerance`。
可以用 `GraphOptimizerConfig(prefer_score_within_tolerance=False)` 关掉、回到父类行为。

## 3. 打分模型：社区房型权重

排班分数除了资源流分项（LMD / EXP / 合成玉 / 赤金 / 碎片平衡），还有一条
`roomEfficiency`：把五类房间的**干员增益百分比**按社区通行比例折算到同一货币，
以贸易站为 1 单位。

| 房型 | 权重（贸易 = 1） | 等价读法 |
| --- | --- | --- |
| 贸易站 | 1.0 | 基准 |
| 制造站 | 1.0 | 1% 制造 ≡ 1% 贸易 |
| 发电站 | 0.5 | 2% 发电 ≡ 1% 贸易 |
| 会客室 | 1/12 ≈ 0.0833 | 12% 会客 ≡ 1% 贸易 |
| 办公室 | 2.0 | 1% 办公室 ≡ 2% 贸易 |

实现要点：

* 锚点不是魔法数字，而是从既有常量推出来的：
  `L3 订单 E[lmd]=1450、E[秒]=12204 ⇒ +1% ≈ +102.66 LMD/天 ⇒ ×(1.5/1000) = 0.154 分`。
  换房间等级时这张表仍然自洽，因为权重是**相对**贸易站的。
* 只统计**干员提供**的百分比（不含每槽 1% 的基础值），因为换算表说的是「百分比为干员增益」。
  `ProductionVector.roomSpeedDays` 记录的就是这个量。
* 只有**价值没被资源流覆盖**的三类会进总分：发电（无人机的资源收益只覆盖它真实价值的
  一小部分）、会客（线索/信用完全没有资源项）、办公室（人脉完全没有资源项）。
  贸易/制造已经在 `lmdGross`/`exp`/`orundum` 里计过价，只作为「等价性对照」
  出现在 `roomEfficiencyDetail` 里，不重复计入。
* 房间级选人目标（`room_output_score`）用同一张表，锚点换成房间分口径
  `×0.0036`，所以「2% 发电 ≡ 1% 贸易」在**选人**层面也成立。

243 平衡搓玉实测（无无人机）：`roomEfficiency = 19.31`，其中
发电 4.81 / 会客 0.64 / 办公室 13.86（贸易 34.88、制造 52.12 仅作对照）。

注意这与旧口径的差异：会客室原来按 `meetingSpeed/30` 计（≈0.033 分/%），
新口径 0.0128 分/%——**比原来低 2.6 倍**；办公室原来 ≈0.033 分/%，新口径
0.308 分/%——**高 9 倍**；发电站原来在总分里是 0，新增 0.077 分/%。
旧的 `office` / `meeting` 两条明细保留不动，用于和既有校准口径对比。

## 4. numpy 加速与磁盘缓存

两者都是可选能力，`pyproject.toml` **没有**新增依赖。

* **numpy**：`graph_conv.py` 里 `try: import numpy`，可用时
  ① 图卷积走稠密矩阵路径（`A_r @ H @ W_r`），实测比纯 Python 稀疏传播快 2×；
  ② 岭回归用 `np.linalg.solve`。两条路径**数值等价**（编码器嵌入差 < 1e-17，
  岭回归解差 < 1e-6），测试 `NumpyEquivalenceTest` 守着这一点。
  没有 numpy 时自动回落，功能不变。
* **磁盘缓存**（`graph_cache.py`）：读出层权重 + 机制超边按内容哈希落盘到
  `outputs/graph_model_cache/`，跨进程复用。键里包含图签名、房间规格、拟合超参、
  羁绊基和 `FEATURE_VERSION`，任何一项变了就自动失效。目录不可写时静默降级。
  这对 `recommend` 的进程池路径意义最大——那里每个候选都会新建一个优化器。

| 342 / 极限搓玉 / 3×8h / 无人机 auto | 448.656 | **459.174** | **+2.34%** | 40.68s | 41.47s | 0.755× |

汇总：**3 胜 1 负**，平均分数比 **1.0139**，平均墙钟比 0.851（快 15%），
平均模拟器调用比 **0.757**（少 24%）。

短名单质量（同一模拟器下与全量枚举对比）：

| 房间 | 目标 | 全量组合数 | 短名单组合数 | 全量最优 | 短名单最优 | 命中 |
| --- | --- | --- | --- | --- | --- | --- |
| TRADING | O_GOLD | 4638 | 75 | 61.645 | 61.645 | 是 |
| TRADING | O_DIAMOND | 4750 | 74 | 282.000 | 282.000 | 是 |
| MANUFACTURE | F_EXP | 4724 | 75 | 38.880 | 38.880 | 是 |
| MANUFACTURE | F_DIAMOND | 4900 | 80 | 99.840 | 99.840 | 是 |

即：把每个房间的候选组合从 ~4800 个压到 ~130~170 个，**最优分完全不变、top16 召回 1.0**。
分数差异来自候选集合的细微变化如何被下游 beam / 插入搜索放大（见 §6 第 5 条）。

## 5b. 排班语义的现状：换班 / 宿舍 / 办公室

这一节回答「模型到底考虑了什么、没考虑什么」，避免误读分数。

**换班是静态分区，不是时间轴模拟。** 约束是「相邻班次不得共用同一干员，且末班与首班
也不重叠」（`_active_boundaries_are_valid`）。对 2 班 / 3 班来说，这在数学上等价于
**每人每天只上 1 个班**。没有「几点换班、换给谁」的时序，也没有「连续上岗多久会掉心情」。

**宿舍不参与收益模型。** `ProductionSimulator.evaluate()` 只遍历 `shift.rooms`。
宿舍技能只有两条路影响结果：① 中枢全局效果里的「全基建阵营计数」和 mujica 活跃度；
② 优化器用「恢复+N ×10」给宿舍排序，决定谁去休息——但这个分数不反馈到产能或疲劳。

**菲亚梅塔的换心情没有建模。** 她的 `自律`（自身恢复+2/h、屏蔽其他恢复）只贡献宿舍排序分；
`患难之交`（满心情时与同宿舍前一位干员互换心情）`parsed_score = 0`，等价于未建模。
根因是整个模型没有「心情状态」，疲劳只是每个班次一次性算出的 `-fatigueRisk × 2` 罚分。

**办公室（人力资源办公室）现在有独立价值了。** 之前它只靠
`officeSpeed/30`（≈0.033 分/%），房间级目标里更是只算 `-fatigue×2`；
现在按「1% 办公室 ≡ 2% 贸易站」进入 `roomEfficiency`（0.308 分/%），
243 平衡搓玉里办公室贡献 13.86 分（旧口径 1.53 分）。
但**选人逻辑仍是「按人脉资源解析百分比排序」**，还没有走加权房间分，
也不吃中枢的 `control_hire_spd` 加成——这是下一步要处理的。

## 6. 已知差距

1. **墙钟时间没有优势，模拟器调用明显减少。** 短名单组装是 Python 层的工作（枚举 + 查表 +
   变体选择），而旧算法的 `itertools.combinations` 和模拟器调用都在 C 层；
   在 4000+ 组合的规模下，纯 Python 的常数因子吃掉了理论上的 60× 优势。
   实测模拟器调用降到 0.54~0.77 倍，但墙钟约 1.0~1.2 倍。
   后续若把读出层的前向搬到 numpy（或直接把短名单缓存成「房间规格 → 组合列表」的持久表），
   墙钟才会真正下降。
2. **合成玉贸易站是零梯度房间。** guide 刊例把 L3 合成玉贸易站固定成 132%，与干员无关，
   所以模型对它只能给常数，选择等于随机。这不影响总分（任何组合分数相同），
   但意味着图模型对该房间没有实际贡献。
3. **阶跃型羁绊只能靠注入，不能靠学。** 16 行龙门币刊例表、3 行制造刊例表是硬编码先验，
   新干员/新机制出现时需要同步维护那张表——这一点旧算法同样依赖。
4. **插入搜索的预算是有损的。** 预算 48 组 / 4 轮相比父类的 64 组 / 8 轮会漏掉排在后半段的
   插入机会。实测它虽然更快，但最终分数对插入顺序高度敏感（同一批场景里波动 ±3%），
   所以**默认关闭**，只在 `limit_insertion_search=True` 时启用。
5. **最终分数对「同分组合的先后」高度敏感。** L3 合成玉贸易站有 4750 个组合全都 282.0，
   哪个三人组进前 64 完全由排序决定，并一路放大到整张表（±3%）。缓解办法是
   `lexicographic_prefix`：把父类枚举顺序的前 96 个组合也塞进短名单，让同分区间的
   先后与父类对齐（这就是 top16 召回从 0.71 提到 1.0 的原因），但没有完全消除。
6. **拟合样本数不是越大越好。** 288 → 1536 样本让 holdout R² 从 0.82 升到 0.89、
   MAE 从 2.4 降到 1.5，但最终排班分数系统性下降约 4%：模型越锐利，短名单越集中在
   同一批干员上，下游搜索失去多样性。所以默认仍是 288。
